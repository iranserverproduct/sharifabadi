## ۱. اطلاعات زیرساخت و وضعیت فعلی ایران سرور

این موارد را خود واحد محصول در جلسه گفت:

- زیرساخت سرورهای ابری: **OpenStack**
- Block Storage: **Ceph**
- Object Storage: **سازگار با S3**
- فروش و صورت‌حساب: **WHMCS**
- پرداخت ساعتی: فعلاً **فقط برای سرورهای گرافیکی (GPU)**؛ برای سرورهای ابری در برنامه است.
- نمایندگی سرور ابری: از طریق **API سرورهای ابری** و **گروه کاربران WHMCS** که به نماینده‌ها روی محصولات تخفیف می‌دهد.
- «برنامه‌ی آماده»: روی **Kubernetes**؛ هر برنامه روی یک کانتینر، تحویل با **زیردامنه‌ی ایران سرور**؛ کاربر به کانتینر دسترسی ندارد و فقط به خود نرم‌افزار دسترسی دارد.
- پرووایدرهای فعلی: **Hetzner** و **OVH**. پرووایدر پیشنهادی **ishosting** هنوز اجرایی نشده.
- شراکت با یاندکس: پیشنهاد خود یاندکس است و از نظر واحد محصول مشکلی ندارد.

سبد فعلی ایران سرور (از منوی سایت iranserver.com):
- هاست (وردپرس، ووکامرس، پایتون، دانلود، ایمیل، بکاپ، ویندوز و لینوکس، نمایندگی هاست)
- دامنه (بیش از ۴۰۰ پسوند، نمایندگی دامنه)
- سرور مجازی: ایران، اروپا، فرانسه، آلمان، فنلاند، آمریکا؛ VPS ترید و GPU
- سرور اختصاصی: ایران، آلمان، فنلاند، فرانسه، کانادا، آمریکا (OVH و Hetzner)
- سرویس‌های ابری: سرور ابری ایران، سرور ابری GPU، Kubernetes (KaaS)، CDN، Block و Object Storage، BareMetal (BMaaS)
- برنامه‌های مدیریت‌شده: n8n، Rocket.Chat، Nextcloud، Grafana، Metabase
- سایر: SSL، لایسنس، کولوکیشن، اجاره‌ی رنج IP، خدمات امنیتی و DevOps

## ۲. آیا یاندکس وب‌سرویس کامل برای پرووایدر شدن دارد؟

**جواب: از نظر فنی بله؛ لایه‌ی پلن، صورت‌حساب و تمدید را باید خودمان بسازیم.**

| نیاز ایران سرور | API یاندکس | وضعیت |
|---|---|---|
| کاتالوگ و قیمت | `Billing SkuService.List`: هر SKU با واحد قیمت، قیمت پله‌ای، تاریخ اعمال؛ ارز RUB، USD یا KZT؛ با `billingAccountId` قیمت قراردادی | کامل |
| ساخت حساب برای هر مشتری | `Billing CustomerService`: `CreateResellerServed`، `Invite`، `List`، `Activate`، `Suspend` | کامل |
| ساخت فضای مشتری | `ResourceManager Cloud.Create` و `BillingAccount.BindBillableObject` | کامل |
| خرید و تحویل | `Compute Instance.Create`؛ همه‌ی عملیات async و Operation برمی‌گردانند | کامل |
| اکشن‌ها | Start، Stop، Restart، Update، دیسک، کارت شبکه، One-to-one NAT، کنسول سریال، Move، Relocate | کامل |
| حذف | `Instance.Delete` و حذف دیسک و Cloud | کامل |

**چیزهایی که API ندارد و باید خودمان بسازیم:**
- **پلن ثابت و موجودی (stock) وجود ندارد.** مدل یاندکس ساعتی است؛ پلن‌ها را از ترکیب SKUها می‌سازیم. به‌جای موجودی، **کوتا** وجود دارد.
- **تمدید دوره‌ای وجود ندارد.** سررسید و قطع سرویس در سیستم ما؛ موقع عدم پرداخت `Customer.Suspend` یا `Instance.Stop` و بعد Delete.
- **محاسبه‌ی مصرف هر مشتری** با ماست؛ یاندکس یک فاکتور تجمیعی به شریک می‌دهد.

**نکته‌ی قراردادی:** قرارداد مشتری یاندکس (نسخه‌ی yandex.com) شرط محل ثبت شرکت و عدم شمول تحریم‌های آمریکا، اروپا، سازمان ملل و سوئیس را دارد و واگذاری به شخص ثالث بدون اجازه‌ی کتبی را منع می‌کند. چون شراکت پیشنهاد خود یاندکس است، شرایط نهایی طبق قرارداد شریک خواهد بود.

**برنامه‌ی شراکت یاندکس:**
- شریک کل مصرف مشتری‌هایش را پرداخت می‌کند (پیش‌پرداخت یا پس‌پرداخت).
- **۲۰٪ پاداش پایه** روی فاکتور شریک (شامل مصرف خود شریک، Marketplace، StoreDoc، Interconnect و گرنت‌ها نمی‌شود).
- تا **۱۵٪ اضافه** با ثبت معامله (Deal registration) و تا ۱۵٪ با ثبت پروژه.
- خروج از برنامه با ۳۰ روز اطلاع قبلی.

## ۳. کوتا (Quota) چیست؟

کوتا **سقف اداری منابع برای هر Cloud** است، نه ظرفیت سخت‌افزاری. دو نوع محدودیت داریم:

| | Quota | Limit |
|---|---|---|
| ماهیت | سقف اداری روی هر Cloud | محدودیت فنی معماری |
| قابل تغییر؟ | بله (کنسول، پشتیبانی، API) | خیر |
| مثال | حداکثر ۱۲ ماشین در Cloud | حداکثر ۹۶ هسته برای یک ماشین |

**کوتاهای پیش‌فرض هر Cloud:**

| منبع | پیش‌فرض |
|---|---|
| ماشین مجازی | ۱۲ |
| vCPU (پلتفرم استاندارد) | ۳۲ |
| RAM | ۱۲۸ GB |
| SSD | ۲۰۰ GB |
| HDD | ۵۰۰ GB |
| تعداد دیسک | ۳۲ |
| IP عمومی (کل / ثابت) | ۸ / ۲ |
| GPU و Compute Optimized | ۰ |
| Snapshot | ۳۲ عدد، مجموعاً ۴۰۰ GB |
| عملیات هم‌زمان در هر Folder | ۱۵ |
| Cloud در هر سازمان | ۵ |
| Folder در هر Cloud | ۵۰ |

**چه چیزی جلوی ساخت ماشین را می‌گیرد:**
1. پر شدن کوتا (رایج‌ترین)
2. Limit فنی هر ماشین (۳۲ تا ۹۶ vCPU، ۲۵۶ تا ۱۲۸۰ گیگ RAM بسته به پلتفرم)
3. وضعیت حساب صورت‌حساب (Suspend، فعال‌نشده، بدون موجودی)
4. کمبود ظرفیت واقعی در یک zone (به‌ویژه GPU)
5. سقف ۱۵ عملیات هم‌زمان در هر Folder

**درخواست افزایش با API:** `QuotaRequestService` (Create، Get، List، Cancel). مستندات نمی‌گوید تأیید خودکار است یا دستی.

## ۶. سؤال: کوتا برای کل ایران سرور یا هر مشتری جدا؟

**جواب: هر مشتری فضا و کوتای جدای خودش را دارد.**

```
حساب شریک ایران سرور
  └─ زیرحساب مشتری (CreateResellerServed)
       └─ سازمان اختصاصی مشتری («For 'Customer' subaccount»)
            └─ Cloud مشتری   ← کوتا این‌جا اعمال می‌شود
                 └─ Folderها و منابع (سرور، دیسک، باکت)
```

- کوتا روی **Cloud** است، نه Folder؛ پس «پروژه»ی هر مشتری = یک Cloud جدا.
- فاکتور همه‌ی مشتری‌ها یک‌جا برای ایران سرور صادر می‌شود.
- **کاهش کوتا:** خود ایران سرور از پورتال شریک.
- **افزایش کوتا:** خودکار تیکت پشتیبانی ساخته می‌شود.
- ساخت Cloud و تنظیم کوتا در مستندات از **پورتال شریک** آمده؛ خودکارسازی کامل با API باید از یاندکس تأیید شود.

## ۷. ساخت زیرحساب با وب‌سرویس

**بله، شدنی است.**

**روش ۱ — بدون دخالت مشتری (مناسب ایران سرور):**
```
POST https://billing.api.cloud.yandex.net/billing/v1/customers:createResellerServedCustomer
```
- `resellerId` (اجباری): شناسه‌ی حساب صورت‌حساب ایران سرور
- `name` (اجباری): نام مشتری
- `person` (اجباری): name، longname، phone، email، postCode، postAddress، legalAddress، tin (همه اختیاری)
- پاسخ: Operation (async)؛ باید تا `done: true` دنبال شود.

**روش ۲ — دعوت با ایمیل:**
```
POST https://billing.api.cloud.yandex.net/billing/v1/customers:invite
```
همان فیلدها + `invitationEmail`.

**متدهای دیگر:** `List`، `Activate`، `Suspend`.

**جریان کامل:**
1. `Customer.CreateResellerServed`
2. `Cloud.Create` در سازمان زیرحساب
3. `BillingAccount.BindBillableObject` (اگر خودکار وصل نشده باشد)
4. `Instance.Create` و سایر محصولات

**نامشخص در مستندات (باید تست یا پرسیده شود):**
- نقش لازم (طبق مستندات شریک، نقش owner حساب صورت‌حساب)
- نیاز یا عدم نیاز به تأیید دستی زیرحساب در API
- محتوای `response` در Operation (شناسه‌ی حساب یا سازمان مشتری)

## ۱۱. الگوبرداری از یاندکس برای محصولات بومی روی زیرساخت ایران سرور

### ۱۱-۱. سرور قطع‌شونده (Preemptible) → «سرور لحظه‌ای»

**در یاندکس:**
- حداکثر ۲۴ ساعت عمر، یا زودتر هنگام کمبود ظرفیت؛ در گروه‌ها ۲۲ تا ۲۴ ساعت تصادفی.
- سیگنال ACPI و **۳۰ ثانیه** فرصت خاموشی (پیشنهاد `DefaultTimeoutStopSec=30s`).
- خاموش می‌شود، حذف نمی‌شود؛ دیسک می‌ماند؛ روشن کردن دستی یا خودکار (autohealing در گروه).
- بدون SLA.
- قیمت: vCPU حدود **۷۳٪** و RAM حدود **۷۵٪** ارزان‌تر.
- کاربرد: CI/CD، رندر، پردازش داده، آموزش مدل زیر ۲۴ ساعت.

**تعریف محصول بومی:**
| ویژگی | پیشنهاد |
|---|---|
| نام | «سرور لحظه‌ای» یا «سرور اقتصادی قطع‌شونده» |
| تخفیف | شروع ۵۰٪، بعداً تا ۷۰٪ |
| عمر | حداکثر ۲۴ ساعت |
| اخطار | ۳۰ ثانیه ACPI + پیامک یا وب‌هوک |
| بعد از توقف | دیسک می‌ماند؛ فقط هزینه‌ی دیسک |
| گزینه‌ی ویژه | «روشن‌شدن خودکار وقتی ظرفیت آزاد شد» |
| ممنوعیت | ماینینگ |
| پرداخت | ساعتی از کیف پول تومانی |

بزرگ‌ترین فرصت: **GPU لحظه‌ای**؛ GPU در ایران کمیاب است و صورت‌حساب ساعتی GPU از قبل وجود دارد.

### ۱۱-۲. سرور ساعتی در برابر سرور لحظه‌ای

| | سرور ساعتی | سرور لحظه‌ای |
|---|---|---|
| موضوع | روش پرداخت | تضمین منابع |
| خاموشی | فقط وقتی مشتری حذف کند | هر وقت ایران سرور ظرفیت لازم داشته باشد، حداکثر ۲۴ ساعت |
| SLA | دارد | ندارد |
| قیمت | تقریباً ماهانه ÷ ۷۲۰ | ۵۰ تا ۷۰ درصد ارزان‌تر از ساعتی |
| مثال یاندکس (۲ هسته / ۴ گیگ) | ≈ $0.031 در ساعت | ≈ $0.008 در ساعت |

- سرور لحظه‌ای همیشه ساعتی است، ولی هر سرور ساعتی لحظه‌ای نیست.
- ترتیب منطقی: اول **سرور ابری ساعتی** (موتور ساعتی از GPU موجود است)، بعد **لحظه‌ای** به‌عنوان نسخه‌ی تخفیف‌دار.
- الگوی **ساعتی با سقف ماهانه** (Hetzner، «max/mo»): ساعتی حساب می‌شود ولی جمع ماه از قیمت ماهانه بیشتر نمی‌شود.

### ۱۱-۳. پیاده‌سازی سرور لحظه‌ای روی OpenStack و Ceph

- **نکته‌ی کلیدی:** در Nova ماشین خاموش (`SHUTOFF`) همچنان منابع را در Placement نگه می‌دارد. برای آزادسازی ظرفیت باید `shelve` + `shelve_offload` زد؛ روشن کردن با `unshelve` (ممکن است روی میزبان دیگر بالا بیاید).
- **Ceph:** flavorهای لحظه‌ای **boot-from-volume** باشند (Cinder روی Ceph) تا shelve تقریباً فوری باشد و داده بماند.

| جزء | پیاده‌سازی |
|---|---|
| علامت‌گذاری | flavor جدا (مثلاً `p.2c4g`) با extra_spec `preemptible=true` یا metadata |
| سقف ظرفیت | سهمیه‌ی ماشین‌های لحظه‌ای در هر aggregate (مثلاً ۳۰٪) |
| سرویس Reaper | گوش دادن به notificationهای Nova روی RabbitMQ؛ با `NoValidHost` برای ماشین عادی، انتخاب کمترین ماشین لحظه‌ای از طریق Placement، اخطار، ACPI، ۳۰ ثانیه، `shelve_offload`، تلاش دوباره |
| سقف ۲۴ ساعت | کرون روی `launched_at` با فاصله‌ی تصادفی |
| IP | port، IP خصوصی و Floating IP معمولاً در shelve متصل می‌مانند (روی نسخه‌ی خودتان تست شود) |
| GPU | shelve، GPU متصل با PCI passthrough را آزاد می‌کند |
| صورت‌حساب | موتور ساعتی GPU با نرخ جدا؛ در حالت shelved فقط دیسک |
| پنل | برچسب، دلیل توقف، دکمه‌ی unshelve، روشن‌شدن خودکار |

- مرجع: پروژه‌ی **Aardvark** از CERN برای preemptible در OpenStack (وضعیت نگهداری تأیید نشده).
- شاخص‌ها: بهره‌وری میزبان، نرخ قطع، درصد روشن‌شدن موفق.
- ریسک‌ها: نارضایتی مشتری، ماینینگ، کمبود ظرفیت در ساعات اوج.

### ۱۱-۴. Serverless Containers → ارتقای «برنامه‌ی آماده» و محصول «کانتینر شما»

**الگوی یاندکس:**
- نسخه‌ها (Revision) تغییرناپذیرند؛ نسخه‌ی قبلی برای بازگشت می‌ماند.
- نمونه‌ی بیکار متوقف و بعد خاموش می‌شود؛ با درخواست دوباره بالا می‌آید.
- نمونه‌ی آماده (Provisioned) برای حذف شروع سرد، با هزینه‌ی جدا.
- حداکثر نمونه و درخواست هم‌زمان (concurrency)؛ بعد از سقف خطای 429.
- فراخوانی با HTTPS، تریگر یا API Gateway؛ برنامه روی پورت `PORT` گوش می‌دهد.
- ایمیج فقط از Container Registry خود یاندکس.

**مقایسه با «برنامه‌ی آماده»ی فعلی:**
| موضوع | الان | پیشنهاد |
|---|---|---|
| روشن بودن | همیشه روشن | پلن اقتصادی با خواب خودکار |
| به‌روزرسانی | — | دکمه‌ی «بازگشت به نسخه‌ی قبل» |
| مقیاس | ثابت | پلن مقیاس خودکار |
| شروع سرد | — | گزینه‌ی پولی «همیشه آماده» |
| دامنه | زیردامنه‌ی ایران سرور | دامنه‌ی اختصاصی + SSL خودکار |
| قیمت | پلن ثابت | پلن ثابت + پرداخت مصرفی |

**کدام برنامه‌ها می‌توانند بخوابند (تخمین، نیاز به تست):**
| برنامه | خواب خودکار | دلیل |
|---|---|---|
| n8n | خیر | کارهای زمان‌بندی‌شده |
| Rocket.Chat | خیر | وب‌سوکت دائمی |
| Grafana | مشروط | فقط بدون alerting |
| Metabase | مشروط | شروع سرد کند (جاوا) |
| Nextcloud | بله | با کرون بیرونی |

**محصول جدید «کانتینر شما» (کاربر ایمیج خودش را می‌آورد):**
- Knative Serving: خواب خودکار، نسخه‌بندی، تقسیم ترافیک
- KEDA: تریگر زمان‌بندی و صف پیام (قابل فروش جدا به‌عنوان «کار زمان‌بندی‌شده»)
- Harbor: رجیستری ایمیج
- cert-manager: SSL خودکار
- Loki و Prometheus: لاگ و متریک در پنل
- ایزوله‌سازی: gVisor یا Kata Containers، NetworkPolicy و ResourceQuota برای هر namespace، ممنوعیت privileged، اسکن ایمیج
- رقابت: PaaSهای ایرانی مثل لیارا؛ تمایز با خواب خودکار یا پرداخت مصرفی
